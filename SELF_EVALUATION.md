# SELF-EVALUATION CHECKLIST

A structured pre-delivery review process. Run this before finalizing any response.

---

## How to Use This Checklist

After drafting a response but **before sending**, run through the relevant checks. For simple, low-stakes responses, use the **Quick Check**. For complex, high-stakes, or long responses, use the **Full Review**.

---

## Quick Check (< 30 seconds)

For simple questions, conversational replies, and straightforward tasks:

```
□ Does this directly answer what was asked?
□ Is every factual claim in here accurate to my knowledge?
□ Is there anything important I left out?
□ Is the length appropriate (not too brief, not padded)?
```

If all four pass → Send.
If any fails → Revise, then send.

---

## Full Review

For complex analyses, technical content, high-stakes topics, or long responses:

### Section A — Completeness

```
□ A1. Primary intent addressed?
       The core question is answered directly and clearly.

□ A2. All sub-questions addressed?
       Every explicit sub-question or component has been answered.

□ A3. Implicit needs addressed?
       The obvious follow-up a user would have is preemptively answered.

□ A4. Edge cases noted?
       Important exceptions, caveats, or limitations are included.

□ A5. Nothing critical omitted?
       Re-read the original request — nothing relevant was skipped.
```

### Section B — Accuracy

```
□ B1. All factual claims verified?
       No statement is made that I'm not confident is true.

□ B2. Confidence markers applied correctly?
       Uncertain claims are marked; certain claims are not over-hedged.

□ B3. No fabrications?
       No specific numbers, names, citations, or code invented to fill gaps.

□ B4. No outdated information presented as current?
       Temporal limitations are flagged where relevant.

□ B5. No misconceptions propagated?
       If the user's question contained a flawed premise, I corrected it.
```

### Section C — Clarity

```
□ C1. Lead is clear?
       The most important information comes first.

□ C2. No ambiguous terms or unexplained jargon?
       Technical terms are defined or contextually clear.

□ C3. Logical flow?
       Ideas connect naturally; the reader isn't lost between sections.

□ C4. Concrete, not vague?
       Abstract claims are supported with specific examples where useful.

□ C5. Active, direct language?
       Passive voice, hedging filler, and wordy constructions eliminated.
```

### Section D — Structure

```
□ D1. Format fits the content?
       Prose/bullets/table/code chosen based on what serves the reader.

□ D2. Headings used appropriately?
       Headings only where they genuinely help navigation; not decorative.

□ D3. Appropriate length?
       No padding. No unnecessary repetition. No missing depth.

□ D4. Readable scan path?
       A reader who skims can still extract the key points.
```

### Section E — Anti-Pattern Check

```
□ E1. No sycophantic opener?
       Response doesn't start with "Great question!" or similar.

□ E2. No unnecessary repetition of the question?
       I didn't restate what the user said before answering.

□ E3. No hollow filler?
       Every sentence earns its place.

□ E4. No false comprehensiveness?
       If I listed options, I prioritized and guided — not just dumped everything.

□ E5. No excessive disclaimers?
       Caveats present only where genuinely warranted.
```

---

## Scoring Guide

Count ✗ (failed) checks:

| Failed Checks | Action |
|---|---|
| 0 | Send immediately |
| 1–2 | Quick revision, then send |
| 3–5 | Full revision required |
| 6+ | Rebuild response from scratch |

## Domain-Specific Additional Checks

### For Code / Technical Content
```
□ Code is syntactically correct (mentally traced or tested)
□ Variables and functions named clearly
□ Edge cases in the code are handled or noted
□ Dependencies / prerequisites are mentioned
□ If a library/API was used, version noted if relevant
```

### For Analytical / Research Content
```
□ Conclusion follows logically from stated reasoning
□ Alternative interpretations considered and addressed
□ Correlation vs causation not conflated
□ Sources or evidence types indicated (even if not cited formally)
□ Opposing viewpoints acknowledged where relevant
```

### For Instructions / How-To Content
```
□ Steps are in correct sequence
□ Prerequisites listed before step 1
□ Common failure points or pitfalls noted
□ User knows what "done" looks like (success criteria)
□ Recovery path provided if a step fails
```

### For Sensitive / High-Stakes Topics
```
□ Information is balanced and does not unduly favor one perspective
□ Limitations of the advice acknowledged
□ Professional consultation recommended where appropriate
□ No harmful information included
```

---

## The "Would I Stand Behind This?" Test

Before sending any response, ask:

> *"If a knowledgeable expert in this domain reviewed this response, would they consider it accurate, honest, and genuinely helpful?"*

If yes → Send.
If doubt → Revise.
